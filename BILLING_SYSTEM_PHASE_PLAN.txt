ContentAgent Billing System - Phase-by-Phase Plan

Core commercial rule for all phases:

$1 = 1,000 CA credits
default markup = 2x provider cost
user_charge_credits = ceil(provider_cost_usd * markup * 1000)

Example:
Provider cost: $0.30
User charge: $0.60
Credits deducted: 600 credits

The backend must always be the source of truth. The frontend only displays estimated credit cost.


============================================================
PHASE 1 - BILLING FOUNDATION
============================================================

Goal:
Create the base billing system without Stripe and without charging live API calls yet.

Build:

1. Credit ledger

Create an append-only ledger. Do not rely only on a mutable workspace.credits number.

Ledger fields:
- id
- userId
- workspaceId
- type: purchase | subscription_grant | usage | reserve | release | refund | admin_adjustment | bonus
- module
- provider
- action
- credits
- usdCost
- markup
- status
- relatedId
- stripePaymentIntentId
- stripeSubscriptionId
- providerTaskId
- description
- metadata
- createdAt
- expiresAt

Credit types:
- subscription_credits: monthly credits from plan, expiry configurable, recommended 90 days
- topup_credits: one-time purchased credits, recommended no expiry
- bonus_credits: admin/manual/promo credits, expiry configurable
- reserved_credits: temporarily held while API call is running

Balance calculation:

available = grants + purchases + bonuses + refunds + releases - usage - active_reserves


2. Rate cards

Create backend-managed rate cards.

Rate card fields:
- id
- provider: kie | apify | upload-post | brevo | stripe | local | custom
- actionType: video_generation | image_generation | text_generation | scrape | persona_crawl | publish | automation_run
- modelOrActorId
- unit: per_action | per_second | per_image | per_1k_tokens | per_1k_results | per_post
- baseCostUsd
- markupMultiplier
- minimumChargeCredits
- roundingMode: ceil
- active
- lastSyncedAt
- source: manual | provider_sync
- metadata


3. Provider mapping

Create a mapping layer so UI labels are not tied directly to provider IDs.

Examples:
- veo-fast -> veo3_fast
- seedance-2.0 -> bytedance/seedance-2
- gpt-image-2 -> gpt-image-2-text-to-image or gpt-image-2-image-to-image

============================================================
PHASE 3 - METERING ENFORCEMENT
============================================================

Goal:
Prevent free or accidental paid provider calls.

Build:

1. Quote -> Reserve -> Settle flow

Every paid API action follows this:

Step 1: Quote
- estimate provider cost
- show credits to user

Step 2: Reserve
- reserve maximum possible credits before API call

Step 3: Provider call
- call Kie / Apify / Upload-Post / other provider

Step 4: Settle
- charge actual cost where available
- release unused credits
- refund if provider did not charge
- follow admin refund policy if provider charged but output failed

Step 5: Log
- save prompt, provider, model, task ID, estimated cost, actual cost, final credits


2. Backend enforcement

Backend blocks all paid API calls unless:
- billing action is configured
- quote exists
- user has enough available credits
- reservation succeeds

If missing billing config:

No billing rate configured for this action.
Please contact admin.


3. No negative balance

Never allow credit balance below zero.


Phase 3 test checklist:
- Paid call cannot run without rate card.
- Paid call cannot run with insufficient balance.
- Reservation is created before provider call.
- Failed pre-provider call releases reservation.
- Successful provider call settles charge.
- Failed provider call records charged/refunded/released status.

============================================================
PHASE 10.5 - STRIPE ACCOUNT AND CATALOGUE MANAGEMENT
============================================================

Goal:
Let an authorized Content Agent admin connect Stripe once and manage the
Stripe product/price catalogue from the Content Agent backend. Complete the
real Stripe test-mode acceptance work before any live payment rollout.


Release boundary:
- Build and deploy Phase 10.5 to staging first.
- Do not enable live payments in this phase.
- Do not replace or remove the Phase 10 webhook/ledger protections.
- Phase 10.5 must pass its acceptance gate before Phase 11 starts.


1. Separate test and live Stripe connections

Replace the single shared Stripe configuration with isolated profiles:

Test profile:
- encrypted test secret key
- optional test publishable key
- Stripe account ID and display name
- webhook endpoint ID
- encrypted webhook signing secret
- optional Customer Portal configuration ID
- connection status and last validation time

Live profile:
- encrypted live secret key
- optional live publishable key
- Stripe account ID and display name
- webhook endpoint ID
- encrypted webhook signing secret
- optional Customer Portal configuration ID
- connection status and last validation time

Rules:
- Never display a complete secret after it is saved.
- Never send a secret key or webhook secret to the browser.
- Never store raw secrets in logs, GitHub, build output, or audit metadata.
- Validate key mode and reject a test key in the live profile or vice versa.
- Preserve environment-variable fallback for emergency recovery.
- Migrate the existing single Stripe settings into the test profile without
  deleting any existing value.


2. Add Stripe connection management to the admin GUI

Add Billing -> Stripe Connection with:
- Test and Live profile cards.
- Connected account name, account ID, mode, and validation status.
- Connect/replace key action.
- Validate connection action.
- Disconnect action with a confirmation dialog.
- Webhook status and last successful delivery.
- Catalogue sync status and last sync time.
- Link to the connected Stripe Dashboard account.
- Explicit warning before any live-mode action.

Connect Stripe workflow:
1. Admin enters the secret key in a masked field.
2. Backend validates it against the Stripe Account API.
3. Backend confirms the key mode and account identity.
4. Admin confirms the account shown.
5. Backend encrypts and stores the key.
6. Backend provisions or verifies the webhook endpoint.
7. Backend stores the returned webhook signing secret encrypted.
8. Backend configures or reuses the Customer Portal configuration.
9. Backend records a secret-safe admin audit event.

The publishable key remains optional while the product uses Stripe-hosted
Checkout. It can be stored for a future embedded Stripe payment form.


3. Isolate test and live webhooks

Use separate endpoint paths:
- /api/stripe/webhook/test
- /api/stripe/webhook/live

Each endpoint must:
- use only its own mode's signing secret
- reject events whose livemode value does not match the endpoint
- store Stripe event IDs for idempotency
- preserve raw request bytes for signature verification
- return quickly and process retry-safe work
- redact customer and secret data from logs

Keep the existing /api/stripe/webhook endpoint temporarily as a compatibility
route during migration. Remove it only after existing endpoints are migrated
and verified.

Required event types:
- checkout.session.completed
- invoice.paid
- invoice.payment_failed
- customer.subscription.updated
- customer.subscription.deleted
- charge.refunded


4. Add backend-managed Stripe catalogue

The Content Agent backend becomes the normal place to manage:
- Starter monthly plan
- Growth monthly plan
- Pro monthly plan
- all one-time credit top-up packages

For each plan/package, store separate test and live mappings:
- Stripe product ID
- active Stripe price ID
- price amount and currency
- recurring interval when applicable
- sync status
- last synchronized time
- catalogue revision ID

Admin actions:
- Create missing Stripe products/prices.
- Sync Content Agent configuration to Stripe.
- Compare Content Agent and Stripe values before applying changes.
- Open the matching Product/Price in Stripe.
- Archive an unused old price.
- Retry a failed synchronization.
- View prior price versions.

Do not require the admin to manually paste Stripe Product or Price IDs during
normal operation. Keep a restricted manual mapping repair action for recovery.


5. Version every price and credit offer

Stripe price amounts are immutable, so changing a price must:
1. Create a new Stripe Price.
2. Keep the previous Price available for historical records.
3. Activate the new mapping only after Stripe confirms creation.
4. Archive the old Price only when it is safe.
5. Record who changed it and the before/after values.

Create an immutable catalogue revision containing:
- internal plan/package ID
- Stripe mode
- Stripe product and price IDs
- charged amount and currency
- base credits
- bonus credits/percentage
- total credits promised
- effective start/end timestamps
- admin actor and reason


6. Snapshot checkout orders before redirecting to Stripe

Create a persistent billing checkout order before opening Checkout:
- user and workspace IDs
- plan/package and catalogue revision IDs
- test/live mode
- Stripe price ID
- exact amount/currency
- exact credits promised
- purchase kind
- checkout session ID
- pending/paid/expired/refunded status
- created/paid timestamps

Webhook credit grants must use this immutable order/revision snapshot. They
must not use the plan/package's latest editable credit amount. This prevents an
admin price edit during Checkout from changing what the customer receives.


7. Handle subscription price changes explicitly

When an admin changes a recurring plan price, require one choice:
- New customers only: existing subscriptions keep their current Stripe price.
- Next renewal: schedule existing subscriptions to move at renewal.
- Change now: migrate selected subscriptions with an explicit proration choice.

Before applying:
- show affected subscriber count
- show old/new price and credits
- show the proration behavior
- require a second confirmation for live mode

Store a migration job with per-subscription result, retry state, and audit log.
Never silently migrate existing subscribers.


8. Permissions and operational safety

- stripe.view
- stripe.connectTest
- stripe.manageTestCatalogue
- stripe.connectLive
- stripe.manageLiveCatalogue
- stripe.migrateSubscriptions
- stripe.disconnect
- stripe.viewEvents

Owner/super-admin can receive all permissions. Other admin roles must be

Add safety controls:

- Confirmation phrase for live catalogue or subscription changes.
- Idempotency keys for all Stripe write operations.
- Retry-safe catalogue synchronization.
- No destructive deletion of Stripe Products/Prices.
- Audit records for connection, sync, price, migration, and webhook changes.

============================================================
PHASE 12 - REPORTING, RECONCILIATION, AND FINANCE AUDIT
============================================================

Goal:
Give admins reliable revenue, cost, margin, credit-liability, and Stripe
reconciliation reporting based on immutable financial records.


1. Define finance metrics precisely

Document and calculate:
- Gross sales: successful Stripe charges before refunds and fees.
- Refunds: full and partial refunded amount.
- Net sales: gross sales minus refunds.
- Stripe fees: processing fees from Stripe balance transactions.
- Net cash: Stripe net amount after refunds/fees.
- Subscription revenue and top-up revenue separately.
- Provider cost: actual provider cost where available; approved rate-card cost
  otherwise.
- Gross margin: net sales minus provider cost and configured direct costs.
- Credits sold, granted, consumed, expired, refunded, and adjusted.
- Credit face-value liability and estimated provider-cost liability.
- MRR, active subscriptions, new subscriptions, upgrades, downgrades,
  cancellations, and churn.

Keep finance definitions visible in the admin report so numbers are auditable.


2. Add Stripe reconciliation data

Persist/synchronize references needed to reconcile:
- Checkout Sessions
- PaymentIntents and Charges
- Invoices and Subscriptions
- Refunds
- Stripe Balance Transactions and fees
- Payout IDs/status where needed
- Content Agent checkout orders
- Content Agent credit ledger entries

Add a scheduled reconciliation job that compares Stripe with Content Agent and
creates discrepancy alerts. It must not automatically rewrite financial data.

Discrepancy examples:
- Stripe payment succeeded but no credit grant exists.
- Credit grant exists but Stripe payment is not paid.
- Amount/price/currency mismatch.
- Duplicate credit grant.
- Refund without matching credit reversal.
- Subscription status mismatch.
- Unprocessed or repeatedly failing webhook.


3. Admin reporting dashboards

Add date range and test/live filters to:
- Revenue overview by day/week/month.
- Subscription versus top-up revenue.
- Stripe fees, refunds, and net cash.
- Provider cost by provider/model/action.
- Gross margin by provider, module, model, and user segment.
- Credit movement and active liability.
- Automation spend and margin.
- Failed generation cost and refund/release totals.
- High-spend and high-cost users.
- Subscription MRR/churn and plan distribution.
- Stripe webhook and reconciliation health.

All report totals must drill down to the underlying immutable rows.


4. User and transaction audit views

Allow an authorized admin to trace one transaction end-to-end:
Stripe payment -> checkout order -> catalogue revision -> credit grant ->
feature reservation -> provider call -> final charge/release/refund -> balance.

User audit should show:
- purchases/subscriptions
- granted/bonus credits
- usage by module/provider
- refunds/adjustments/expiry
- current calculated balance
- Stripe and provider references
- admin actions affecting the account


5. Exports and finance operations

Add permission-controlled CSV exports for:
- credit ledger
- sales and refunds
- invoices/subscriptions
- provider costs
- margin report
- credit liability
- reconciliation discrepancies

Exports must:
- respect selected date range/mode/filters
- include report generation timestamp and currency
- redact secrets and sensitive payment/customer fields
- record an audit event identifying the exporting admin


6. Alerts and scheduled controls

Create alerts for:
- failed or delayed Stripe webhooks
- unreconciled successful payments
- duplicate ledger candidates
- negative or inconsistent balance attempts
- margin below configurable threshold
- provider cost spikes
- high refund/payment-failure rates
- credit liability above configurable threshold

Show alerts in Admin and optionally email critical alerts through Brevo.


7. Data integrity and close procedure

Add a repeatable daily/monthly close report:
- opening credit liability
- credits sold/granted/consumed/expired/refunded/adjusted
- closing credit liability
- Stripe gross sales/refunds/fees/net
- provider cost and gross margin
- unresolved discrepancy count/value

Closed periods remain immutable. Corrections use dated adjustment entries with
an actor, reason, and link to the original record.


Phase 12 acceptance checklist:
- Revenue totals reconcile to Stripe for a selected period.
